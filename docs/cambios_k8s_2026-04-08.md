# Bitacora de cambios y movimientos (2026-04-08)

Este documento resume exactamente los cambios y acciones ejecutadas para dejar el flujo de despliegue en Kubernetes funcionando en este repo.

## 1) Objetivo de la intervencion

- Poner el proyecto en contexto completo.
- Validar que `kubectl` estaba activo.
- Alinear el flujo a Kubernetes real del entorno.
- Resolver fallos de despliegue (namespace, probes, carga de modelo MLflow).
- Dejar un camino reproducible para despliegues futuros.

## 2) Diagnostico inicial realizado

Se revisaron:

- Estructura completa del repo (`docs/`, `k8s/`, `gateway/`, `model_service/`, `src/`, `scripts/`).
- Documentacion de despliegue:
  - `docs/mlflow_to_k8s_workflow.md`
  - `docs/bentoml_yatai_quickstart.md`
- Scripts clave:
  - `k8s/build_images.sh`
  - `k8s/deploy_gateway.sh`
  - `k8s/deploy_model.sh`
  - `scripts/register_model_from_run.sh`
  - `deploy_model.sh` (raiz)
- Servicios:
  - `gateway/service.py`
  - `model_service/service.py`
- Referencia de fallback de version:
  - `src/1_descargar.py`

Hallazgos:

- `kubectl` instalado y activo sobre contexto `docker-desktop`.
- Namespace real en cluster: `api-models`.
- El repo mezclaba defaults/documentacion entre `ml-serving`, `api-model` y `api-models`.
- En MLflow los modelos estaban registrados, pero sin stage `Production` (`None`), por lo que `latest -> Production` podia romper.
- Probes de K8s apuntaban a `/health` y Bento respondia `405` en liveness/readiness.
- `model_service` no tenia dependencias suficientes para el modelo (faltaba `tensorflow` y habia mismatch de versiones).

## 4) Cambios de codigo y config aplicados

## 4.1 `model_service/service.py`

Cambios:

- Se reescribio el servicio para:
  - soportar `MODEL_URI` opcional (ej: `runs:/<run_id>/model`)
  - resolver `MODEL_VERSION=latest` con fallback robusto:
    1. usar ultima version en `Production` si existe
    2. si no, usar la mayor version numerica registrada
- Se anadio uso de `MlflowClient`.
- Se ampliaron datos devueltos por `health` (`model_version`, `model_uri`).

Motivo:

- Replicar idea de `src/1_descargar.py` (obtener ultima version disponible) pero dentro del servicio de inferencia en K8s.

## 10) Incidencia y correccion de prediccion (2026-04-09)

Incidencia reportada:

- Llamando al gateway con:
  - `model_name=nitrate_nowcasting_best_01`
  - `data.features=[1.0,2.0,3.0]`
- Respuesta:
  - error `400 Bad Request` hacia `http://model-nitrate-nowcasting-best-01:3000/predict`

Causa raiz 1:

- `gateway/service.py` reenviaba el body al model-service como `{"features": ...}`.
- `model_service` (Bento API) esperaba `{"data": {...}}` por la firma `predict(self, data: dict)`.

Correccion aplicada 1:

- `gateway/service.py` actualizado para reenviar:
  - `json={"data": data}`
- Afecta a:
  - `predict`
  - `batch_predict`

Despliegue aplicado:

- imagen nueva: `model-gateway:fix1`
- rollout de `deployment/gateway`

Causa raiz 2 (despues del fix 1):

- El modelo en si espera tensor con forma `(24, 12)` por muestra.
- Payload 1D (`[1,2,3]`) no cumple shape.
- Ademas, el `model_service` convertia `features` a `DataFrame` y para secuencias devolvia `dtype object`.

Correccion aplicada 2:

- `model_service/service.py` actualizado:
  - si llega `features`, convierte a `numpy.float32`
  - soporta entradas 1D / 2D / 3D
  - 2D se transforma a `(1, timesteps, n_features)` para una muestra temporal

Despliegue aplicado:

- imagen nueva: `model-service:fix2`
- rollout de `deployment/model-nitrate-nowcasting-best-01`

Validacion final:

- peticion con `features` de forma `24x12` responde correctamente, por ejemplo:
  - `{"model":"nitrate_nowcasting_best_01","predictions":[[0.3411591351032257]]}`

## 11) Mejora de /list_models + utilidades REST y modelo tiny (2026-04-09)

Problema:

- `/list_models` devolvia vacio (`configured_models=[]`, `endpoints={}`), aunque habia modelos desplegados por convencion.

Cambios en gateway:

- `gateway/service.py`:
  - `list_models` pasa a ser `async`.
  - Se anadio discovery de servicios `model-*` en Kubernetes via API interna del cluster.
  - Se anadio salida estructurada:
    - `discovered_models`
    - `recently_routed_models`
    - `discovery.status/error`
    - `endpoints` combinados.

Problema RBAC detectado:

- Discovery devolvia `403 Forbidden` al listar servicios desde el pod.

Correccion RBAC:

- En `k8s/deploy_gateway.sh` se anadieron:
  - `ServiceAccount` (`gateway-sa`)
  - `Role` con `get/list` sobre `services`
  - `RoleBinding` en namespace del gateway
  - `serviceAccountName: gateway-sa` en Deployment

Validacion final de `/list_models`:

- Discovery en estado `ok`.
- Modelo detectado:
  - `nitrate_nowcasting_best_01`
- Endpoint detectado:
